## 1. Problem Statement

ChordLab currently renders a piano keyboard, but pressing a key only logs a MIDI value. Users need to select notes visually, understand which notes are active, and submit that note set as a chord input.

## 2. Goals

- Make piano keys selectable with mouse and keyboard input.
- Show selected notes with a clear, non-color visual state.
- Provide clear and submit actions.
- Expose a stable selected-note set to other features.

## 3. Non-Goals

- External MIDI controller support.
- Automatic chord naming, voicing search, or audio playback.
- Piano recording or key-pressure behavior.

## 4. Personas & User Stories

- **As a pianist**, I want to click notes so I can enter a chord.
- **As a beginner**, I want selected keys and note names to be visible so I understand what I entered.

## 5. Functional Requirements

- **FR-1.** Clicking a piano key MUST toggle its selected state.
- **FR-2.** Each key MUST expose its note name and MIDI value to assistive technology.
- **FR-3.** Selected keys MUST use both a visual style and an accessible pressed state.
- **FR-4.** Clear MUST remove every selected note.
- **FR-5.** Submit MUST emit selected notes in ascending MIDI order.
- **FR-6.** The interface MUST handle the existing 36-key range without clipping on mobile.

## 6. Non-Functional Requirements

- **Accessibility** — keys MUST be keyboard reachable, labeled, and operable without a mouse.
- **Performance** — toggling a key SHOULD update the visual state within 100 ms.
- **Responsive** — the keyboard MUST remain usable at narrow widths through controlled horizontal scrolling inside its panel if needed.

## 7. Acceptance Criteria

- **AC-1.** Given an empty keyboard, when C, E, and G are activated, then all three keys appear selected.
- **AC-2.** Given selected notes, when Clear is activated, then no keys remain selected.
- **AC-3.** Given selected notes, when Submit is activated, then one ordered note-set event is emitted.
- **AC-4.** Given keyboard-only use, when a key receives focus and Space is pressed, then that key toggles without submitting the page.
- **AC-5.** Given a narrow screen, when the piano renders, then keys remain reachable and the surrounding page does not overflow horizontally.

## 8. Data Model

Use a client-only `PianoInput` model containing selected MIDI numbers, derived note names, and input status. No persistence is required.

## 9. API Surface

No server route. Expose a typed callback for selected-note submissions.

## 10. UI / UX

Extend `src/components/PianoKeyboard.tsx` with selected, focused, clear, submit, empty, and validation states. Show the current note names beside the keyboard.

- Replace the current log-only callback with selected-note state.
- Rollback by restoring the display-only keyboard while retaining the component boundary.

## 16. Test Plan

- **Unit** — toggle, clear, MIDI ordering, and note-name conversion.
- **Integration** — submitted notes reach the parent feature.
- **End-to-end** — select a triad, clear it, and submit another note set.
- **Accessibility** — keyboard activation, focus visibility, labels, and `aria-pressed`.
- **Manual exploratory** — desktop, mobile, black keys, rapid toggling, and empty submission.
